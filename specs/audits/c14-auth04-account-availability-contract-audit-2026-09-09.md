## Timezone repair is part of the build

Weekly generation uses `availability.timezone`; the following consumers still use `tzForState`. An explicit timezone differing from the state can therefore produce one set of windows and a different local day/period for exclusions or displayed confirmations.

| Consumer | Existing source |
|---|---|
| Weekly generation | `lib/quote/availability.ts:286`; `lib/quote/slots.ts:218` |
| Generic quote picker and booking validation/exclusions | `app/q/[token]/book/page.tsx:166`; `app/api/q/[token]/book/route.ts:171` |
| Redirect booking availability count | `app/r/[token]/[tier]/route.ts:528` |
| Roofing/painting picker and exclusions | `lib/quote/trade-booking.ts:48`; consumers under `app/q/{roof,paint}/[token]/book` |
| Native/web calendar timezone DTO | `app/api/tenant/calendar/route.ts:347` returns the state zone, consumed as `tenantTz` |
| SMS booking labels | `lib/quote/booking-notify.ts:107`; `app/api/q/book/[trade]/[token]/route.ts:170` |
| Customer quote/thanks labels | `app/q/[token]/page.tsx:1495`, `app/q/[token]/thanks/page.tsx:187`, and the corresponding roofing/painting page and thanks routes |
| Trade visit ICS labels | `lib/quote/visit-ics-response.ts:32`, both trade visit.ics routes and their tenant identity DTO |

Create one server-owned availability context resolver and use it in generation, exclusions, accepted-slot validation, calendar, confirmation labels and ICS adapters. Return the effective mode and explicit zone rather than making the device infer them. Preserve the legacy exact-slot branch and existing booked ISO instants; do not silently rewrite historical bookings when settings change. Inspect the generic `app/api/q/[token]/ics/route.ts` and shared `calendar-links.ts` together with the trade ICS adapters. Tests must cover a state/weekly-zone mismatch and Sunday hours around both DST transitions; the current single-offset wall-clock conversion needs that evidence before arbitrary working hours/timezones are accepted.

Do not expose timezone editing while only the settings writer has changed. Ship the paired consumers together, or leave that capability explicitly unavailable. A hidden state-derived default is not equivalent to completed timezone support.

## Recommended bounded implementation

1. **Own availability contract.** Add a narrow owned `/api/tenant/business-availability` GET/PATCH and operation-status GET, following the verified C13 ownership pattern. GET returns verified `userId`/`tenantId`, a revision, stored-template state (including invalid legacy data), effective mode (`weekly`, `legacy_curated` or `legacy_rolling`), effective zone/context, the server's proposed weekly template, and supported timezone/capability data. The rolling/curated distinction is computed using server time; do not turn passage of time into a settings write or falsely mark the proposed template as saved.
2. **Atomic authority and recovery.** Use a dedicated availability revision rotated on changes to `default_availability`, `available_slots` and `state`, including legacy `/me`, onboarding/admin/direct SQL updates and A→B→A changes. Under the owned tenant row lock, bind a request UUID to actor, tenant, expected revision and canonical exact input hash. Apply only the submitted availability fields and record the result in the same transaction. Same operation returns its original complete/rejected result after later edits; changed identity reuse is rejected. Persist revision conflicts as terminal rejections. GET operation status must be non-enumerating for another owner/tenant. Readiness/missing migration fails before writes; pause permits recovery reads; service RPC ACLs and receipt-table DML restrictions require actual role tests.
3. **Lossless hours and strict validation.** Use the existing seven fixed day keys, version and nullable HH:MM fields. Disabling toggles `enabled` only and retains remembered start/end through write/refetch/remount. Enabling a day with no remembered pair requires a complete valid pair; any suggested times come from the explicit server proposal. Validate all supplied time strings, enabled start/end order and supported IANA zones without stripping unknown fields. Keep malformed local edits in the encrypted working copy, never silently normalize them into saved values. Distinguish all-days-disabled from absence.
4. **Native account and shared onboarding form.** Add a seven-day editor, explicit timezone choice, effective-mode explanation and explicit Save. A legacy account must see that saving the weekly template changes its existing exact-slot booking mode. Use verified current GET before new writes, encrypted scoped working copies, synchronous submit latch and account/session epochs. Retain only opaque request/revision/hash identity with no expiry for unknown writes; remount/status is GET-only. A not_found response cannot permit a new operation. Exact same-operation retry requires the original input; changed edits stay preserved until the original result is terminal and reconciled. Do not acknowledge success from field equality or old `/me` PATCH. Share the form/schema with onboarding, consume `/api/onboard/trades`, and preserve disabled/failed-read readiness states and activation recovery.
5. **Licences as a separate paired C14 transaction.** Return typed per-trade rows plus explicit stored/fallback source; fail on a constituent read error. Define permitted owned trades from actual supported capability data, strict real date-only expiry, and changed-field-only merges under CAS. The revision must cover per-trade INSERT/UPDATE/DELETE, active/primary trade changes and legacy fallback licence/state fields. Preserve all unedited trade rows/books. Fix old `/me` partial-field clearing and explicit-row PDF fallback semantics in the same coordinated server pass; invalidate only eligible draft PDF caches and preserve released artifacts. Native switching trades keeps each scoped draft; an unavailable/removed trade does not silently discard it.
6. **Trade management is not a cosmetic toggle.** Reconcile the desired manageable set in one operation transaction, with a minimum of one managed trade and preserved non-manageable slugs. Reuse actual seeding/defaults and preserve historical work. Stage and display activation/removal consequences before Save. Preserve unrelated books/licences; retain deactivated configuration/history or define and explicitly present any required removal policy before implementing it. Fence legacy producers and registry changes; record the whole result for recovery. Provider prompt refresh is a separate durable follow-up outcome and must not cause a second reconciliation or a false claim that voice provisioning is complete. Do not enable this mutation from native merely because `/trades/available` can be read.

## Required evidence before acceptance

- Actual SQL and actual route tests: owner isolation; effective NULL/invalid/curated/rolling/weekly modes; exact defaults; all seven days; disabled remembered fields; strict HH:MM/timezone/date validation; unchanged licences/books; legacy write revision rotation; same-value ABA; two-editor conflict; full rollback; same-op replay after later updates; changed-ID/hash reuse; missing/revoked RPC; effective client denials and service execution.
- Paired booking tests: state differs from stored zone, device differs from both, half-hour AU zones, daylight-saving gap/overlap, AM/PM exclusion keys, page/API accepted-slot equivalence, calendar labels and ICS instants. Existing booking timestamps survive settings changes.
- Native tests: off/on and save/refetch/remount equality; all-off vs absent; local invalid inputs; old-account token/body replies; unknown completion before/after commit; not_found fencing; exact retry; failed working-copy load/write/clear; newer local edits preserved; field-specific errors; readiness loading/failure and activation-return recovery. Run matched installed-device checks later; source/unit tests do not close REL02/REL05.

Recommended order: availability authority + timezone consumers → native Account/shared form + readiness-gated onboarding → licence authority → atomic staged trade reconcile. These are separate acceptance slices; completing availability does not close C14 or AUTH04 in full. Migration numbers and implementation ownership are intentionally unassigned pending coordination after the current gate.
